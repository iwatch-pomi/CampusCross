## 1. サービス概要

- **名称（仮）**: Campus-Cross（キャンパス・クロス）
- **一言で**: 同じキャンパスにいる「隣の学部の人」と、15〜30分だけ専門を教え合う。お金は介さず、チケットで回す。
- **タグライン案**: 「15分で、となりの学部へ。」

## 2. 解決する課題とコアバリュー

### 課題
- 同じキャンパスにいても、他学部で何が研究・議論されているかが見えない（学びのサイロ化）
- 既存のスキルシェアは「重い・お金が絡む・知らない人で不安」で、学生が気軽に使えない

### コアバリュー
1. **異分野が交わる瞬間をつくる**: 自分の専門を「専門外の人向け」に噛み砕いて話し、相手の分野の視点を持ち帰る
2. **心理的安全性**: 学内メール認証で、相手が同じ大学の学生であることが保証される
3. **超軽量**: 15〜30分・学内で対面・事前のやり取りほぼゼロ
4. **お金を介さない**: 純粋な知的好奇心で動ける。教えることが自分の学び直しと実績になる

## 3. ターゲット（Phase 1）

| 役割 | 想定 | 人数目安 |
|---|---|---|
| 初期スピーカー | 友人・先輩（学部3年〜院生）。理学・工学・情報・文系を最低1人ずつ | 10〜15名 |
| 学び手 | スピーカーの紹介・SNS告知で集まる学部生 | 30〜60名 |

全員が「教える側」にも「学ぶ側」にもなれる。立場はアカウントではなく、セッションごとに決まる。

## 4. 体験の流れ

```
[学内メールでOTPログイン] → [プロフィール登録（学部・分野）] → チケット3枚を受け取る
        │
        ├─ 学ぶ:  ホーム（異分野のカードが上に並ぶ）→ カード詳細 → 空き枠を選んで予約（チケット1枚を仮押さえ）
        │          → 当日、学内で会う → 「完了」＋お礼コメント → 仮押さえ分が教えた人へ移る
        │
        └─ 教える: 募集カードを作る（問い形式）→ オフィスアワーの枠を出す → 予約が入ると通知 → 当日会う → +1枚
```

## 5. トークン（チケット）設計

UI上の呼称は「チケット」（仮）。仮想通貨を連想させる「トークン」は使わない。

### 5.1 ルール

| イベント | 増減 | 備考 |
|---|---|---|
| 新規登録 | **+3** | 1回きり |
| 毎月の配布 | **+1** | 日本時間で毎月1回。**残高が5枚以上の人には配らない**。登録した月は対象外。ログイン時に自動で受け取る |
| 予約する | **−1（仮押さえ）** | 残高0なら予約できない |
| 予約のキャンセル（どちらから） | **+1（返却）** | 学ぶ側からのキャンセルは開始時刻まで |
| セッション完了 | 教えた人に **+1** | 学ぶ側が「完了」を押した時点で確定。開始時刻を過ぎてからのみ押せる |
| 自動完了 | 教えた人に **+1** | 終了から48時間、どちらも何もしなければ自動で完了扱い |

- 教えて得たチケットに上限はない（教える意欲を削がないため）。上限（5枚）は毎月の配布だけに適用し、配りすぎによるインフレを防ぐ。
- 数値（3枚／1枚／5枚／48時間／予約締切1時間前）はすべて設定テーブルで変更できるようにし、検証中に調整する。

### 5.2 流通量の見積もり

スピーカー15人・学び手45人（計60人）の場合:
- 初期発行: 180枚
- 毎月の配布: 最大60枚/月（実際は上限で減る）
- 学び手1人あたり、初月は3回まで、翌月以降は最低でも月1回は予約できる。**「1回で終わる」問題が解消される**

### 5.3 法的な位置づけ（利用規約に明記）

- チケットは換金・売買・譲渡できない
- 金銭や物品との交換はできず、サービス内での予約にしか使えない
- 運営は残高の調整・失効を行うことがある

## 6. 異分野交流を起こす仕掛け

異分野交流を主軸にしたので、偶然の出会いに任せず、UIとデータ設計で交差を起こしにいく。

1. **ホームの並び順**: 自分と**違う分野**のカードを優先して表示する（同じ分野はタブで切り替え）
2. **「異分野」バッジ**: 自分と分野が違うカードに目印をつける
3. **問い形式のカード**: タイトルは「15分でわかる：〇〇って結局なにがすごいの？」のような**問い**にする。テンプレートを用意する
4. **「専門外の人へのひとこと」欄**: 前提知識ゼロで来ていいことを、教える側が明言する
5. **「あなたの分野から聞きたいこと」欄**: 教える側も相手の視点を求めていることを示し、一方的な講義ではなく**交換**にする（例：「情報系の人に、このデータの解析方法を聞いてみたい」）
6. **予約時のひとこと**: 学ぶ側は自分の分野と、聞きたいことを1〜2行添える
7. **異分野かどうかの記録**: 予約ごとに、学ぶ側と教える側の**学部または分野**が違うかを記録し、KPIとして追う（例：同じ工学部でも、分野が情報と機械なら異分野。法学部と経済学部は分野が同じ社会科学でも、学部が違うので異分野）

### 分野の区分（初期値）

理学／工学／情報／生命・農学／医療・薬学／人文／社会科学（法・経済・経営など）／教育／芸術・デザイン／学際・文理融合／その他

「学際・文理融合」は、広島大学の総合科学部のような文理をまたぐ学部のために設けた。

学部は自由入力にせず、運営が自大学の学部一覧を登録し、そこから選んでもらう（表記ゆれを防ぎ、「法学部のしくみ」のように学部で絞り込めるようにするため）。

**広島大学の学部と代表的な分野**（初期データは `supabase/seeds/hiroshima-u.sql`）

| 学部 | 代表的な分野 | 学部 | 代表的な分野 |
|---|---|---|---|
| 総合科学部 | 学際・文理融合 | 理学部 | 理学 |
| 文学部 | 人文 | 医学部 | 医療・薬学 |
| 教育学部 | 教育 | 歯学部 | 医療・薬学 |
| 法学部 | 社会科学 | 薬学部 | 医療・薬学 |
| 経済学部 | 社会科学 | 工学部 | 工学 |
| 生物生産学部 | 生命・農学 | 情報科学部 | 情報 |

代表的な分野はプロフィールの初期値で、本人が変えられる（例：工学部で情報系の研究をしている人は「情報」を選べる）。

### 6.2 カードの種類：「専門テーマ」と「学部のしくみ」

| 種類 | 中身 | 例 | 位置づけ |
|---|---|---|---|
| **専門テーマ**（メイン） | 自分の研究・専門・スキルを専門外向けに噛み砕く | 「15分でわかる：CRISPRって結局なにがすごいの？」 | ホームの中心 |
| **学部のしくみ** | その学部の中にいないと分からない制度や学び方 | 「法学部のゼミってどうやって決まる？」「文学部の卒論ってどんな感じ？」 | ホームの別タブ「他学部のしくみ」 |

**「学部のしくみ」を分ける理由**
- 研究室配属や院試の情報は、理系なら実験のTAや先輩から聞けるため、Campus-Cross の主軸にはしない
- 一方で、**他学部の制度は外からほぼ見えない**。特に文系のゼミや研究室配属の仕組み（時期・選考方法・必修かどうか・卒論の有無）は、理系の学生には想像もつかない。逆に文系から見た理系の研究室配属も同じ
- 他学部の「学び方の仕組み」を知ること自体が異分野を理解することなので、主軸の価値と矛盾しない
- 制度は大学・学部・年度によって違うため、ネットの一般論ではなく**中の人から直接聞く価値**が高い

**「学部のしくみ」カードのテンプレート**（話す内容の目安。全部埋めなくてよい）
1. ゼミ・研究室はいつ、どうやって決まる？（時期、希望の出し方、選考があるか：成績・面接・レポートなど）
2. ゼミ・研究室への所属は必修？ 入らない人もいる？
3. 卒論・卒業研究はある？ どれくらいの分量・期間？
4. ゼミ・研究室での普段の過ごし方（週に何回・何をするか）
5. 卒業後の進路の傾向（就職・院進学など）
6. 他学部の人に「ここが意外」と言われること

**運用ルール**
- チケットのルールは専門テーマと同じ（教えて+1／教わって−1）
- Phase 1 の初期スピーカーには、**文系の学部から最低1人、「学部のしくみ」カードを出してもらう**よう依頼する
- 自分の学部の「しくみ」は、数人分そろえば比べられる（ゼミによって選考が違う、など）。同じ学部から複数人が出すのを歓迎する

## 7. オフィスアワー方式と対面を推す設計

- 教える側は**空き枠**（15分または30分、最長60分）を出す。例：「火曜 12:20〜12:35 中央図書館1F ラウンジ」
- 枠には**場所**の入力が必須。初期値は「対面」で、オンラインは選択肢として残す
- 学ぶ側は、カードと枠を選ぶだけで**承認待ちなしで予約が確定**する。やり取りは不要
- 予約の締め切りは**開始1時間前**（教える側が気づける余裕を持たせる）
- 同じ教える人の枠は時間が重ならない（DBの制約で防ぐ）。自分が予約・担当している時間帯と重なる枠は予約できない
- 場所の候補として、人目のある学内スポット（図書館・学食・ラウンジ）を選択肢として出す

## 8. MVPの機能要件

### Must（Phase 1 に必須）

| # | 機能 | 内容 |
|---|---|---|
| M1 | 学内メールのOTP認証 | 許可リストにある自大学ドメイン（サブドメイン可）のみ登録できる。メールアドレスを学外のものに変更することも禁止 |
| M2 | プロフィール | ニックネーム・学部（マスタから選ぶ）・分野・学年・自己紹介（連絡先は書けない）。性別（非公開・任意）と同性限定の設定。利用規約への同意が済むまで予約やカード作成ができない |
| M3 | 通知先の登録 | 普段使いのメールアドレスを任意で登録。予約・キャンセル・完了の通知を送る |
| M4 | 募集カード | 作成・編集・非公開化。種類（専門テーマ／学部のしくみ）を選び、それぞれのテンプレートを出す。15分か30分か、タグは最大5つ |
| M5 | ホーム一覧 | 「専門テーマ」と「他学部のしくみ」のタブ・異分野を優先して並べる・分野や学部で絞り込む・キーワード検索・「異分野」バッジ |
| M6 | オフィスアワー枠 | 作成・取り消し。場所は「学食・図書館フリースペース・キャンパス内カフェ・Zoom」から選ぶ（最長30分）。ZoomのURLは予約した人だけに表示 |
| M7 | 予約 | 枠の予約（チケットの仮押さえ）・キャンセル（返却）・完了（教えた人へ移る）・お礼コメント |
| M8 | チケット | 残高・履歴の表示、毎月の配布、48時間後の自動完了 |
| M9 | 安全 | 通報・ブロック、相互の安全レビュー、別々の2人からの深刻な通報で自動一時停止、運営による永久凍結（ログイン・再登録も不可）、大学への通報の記録、利用規約・安全ガイドライン（`/guidelines`） |
| M10 | マイページ | 教えた回数・テーマ・受け取ったお礼コメントの一覧（ガクチカの実績として見せられる形） |

### Won't（Phase 1 ではやらない）

- アプリ内チャット（連絡が必要ならお互いの判断で外部に）
- 星の数による公開評価・ランキング（評価のプレッシャーで教える側が減るのを防ぐ。安全のための相互レビューは、相手に見えない形で行う）
- 承認制の予約・日程の交渉
- 他大学への開放・高校生の受け入れ
- ネイティブアプリ（スマホ向けに最適化したWebで十分）

## 9. 予約の状態遷移

```
            book_slot（学ぶ側: −1 仮押さえ）
  [枠: open] ───────────────────────────────▶ [予約: booked] / [枠: booked]
                                                  │
     ┌────────────────────────────────────────────┼─────────────────────────────┐
     │ cancel（学ぶ側・開始前）                    │ cancel（教える側）           │ complete（学ぶ側・開始後）
     ▼                                            ▼                             │ or 終了48時間後に自動完了
 [予約: cancelled] 学ぶ側 +1             [予約: cancelled] 学ぶ側 +1             ▼
 [枠: open に戻る]                        [枠: cancelled]                  [予約: completed]
                                                                           教える側 +1
```

- 学ぶ側が来なかった場合、教える側がキャンセルする（学ぶ側には返却される。Phase 1 では寛容な扱いにする）
- 状態の変更とチケットの移動は、すべてDB関数の中でトランザクションとして実行する。クライアントから残高を直接書き換えることはできない

## 11. 技術構成

| 層 | 採用 | 備考 |
|---|---|---|
| フロントエンド | Next.js（App Router）＋ Tailwind CSS | スマホ向けに最適化 |
| 認証 | Supabase Auth（メールOTP） | **独自SMTP（Resendなど）を必ず設定**。標準の送信は上限が低い |

| 通知メール | Resend（Next.jsのサーバー側から送信） | 予約などのDB関数が成功した後に送る |
| ホスティング | Vercel | |

スキーマとロジックは `supabase/migrations/` にある。設計の詳細は [`supabase/README.md`](../supabase/README.md) を参照。

## 12. KPI と Phase 1 の成功基準（4週間）

| 指標 | 目標 | 意味 |
|---|---|---|
| 成立したセッション数 | **30件以上** | そもそも使われるか |
| 異分野セッションの比率 | **60%以上** | 主軸の価値が起きているか |
| 2回目を予約した学び手の割合 | **40%以上** | また使いたいと思えるか |
| 教える側に回った学び手の割合 | **30%以上** | ギブ＆テイクが循環しているか |
| キャンセル率 | 20%未満 | オフィスアワー方式が機能しているか |
| 完了時のお礼コメント記入率 | 50%以上 | 教える側の動機につながっているか |
| 「学部のしくみ」セッション数 | 参考値（目標なし） | 他学部の制度を知りたいという需要がどれくらいあるか。多ければ Phase 2 で大学をまたいで比べる企画に広げる |

あわせて、終了時に全員へアンケートを取り、「また使いたいか」と「異分野で新しい視点を得られたか」を聞く。

## 13. ロードマップ

- **Phase 1（直近1ヶ月・学内検証）**
  - 第1週: 初期スピーカー10〜15人がカードを作り、枠を出す（開発と並行して、Googleフォームでの手動運用も可）
  - 第2〜4週: 学び手を募って本番運用。週ごとにKPIを確認し、チケットの数値を調整する
- **Phase 2（他大学への展開）**: ドメインの許可リストに大学を追加する。大学をまたいだ分野の交差は、まずオンラインの枠で
- **Phase 3（高校生への展開）**: 未成年との接触・保護者の同意・個人情報の扱いの水準がまったく違うため、**別のサービスとして設計する**
