## 1. サービス概要

**一言で**：同じキャンパスにいる「となりの学部の人」と、15〜30分だけ専門を教え合うサービスです。お金は使わず、チケットで回します。

| 項目 | 内容 |
|---|---|
| 解決したい課題 | 同じ大学にいても他学部の研究や学び方が見えない。既存のスキルシェアは「重い・お金が絡む・知らない人で不安」 |
| 提供する価値 | 異分野の視点に出会う（異分野交流）／自分の専門を説明する経験（ガクチカにもなる）／学内限定の安心感 |
| 料金 | 学生どうしの利用は無料。教えると +1枚、教わると −1枚のチケット制（登録時3枚・毎月1枚配布、**換金・譲渡不可**） |
| 1回の長さ | 15分または30分（最長30分） |
| 実施場所 | 学食・図書館フリースペース・キャンパス内カフェ・Zoom のいずれか（それ以外は選べない） |
| 公開範囲 | 学外には一切公開しない（閲覧にもログインが必要） |

### カードの種類
- **専門テーマ**：自分の研究・専門を専門外の人向けに話す（例：「15分でわかる：機械学習って結局なにがすごいの？」）
- **学部のしくみ**：ゼミ・研究室の決まり方、卒論の有無など、その学部の中の人しか知らない制度の話

## 2. 利用の流れ

1. 大学のメールアドレスに届く6桁のコードでログインする（パスワードなし）
2. プロフィール（ニックネーム・学部・学年・分野）を登録し、**利用規約・安全ガイドラインに同意する**
3. 話す側は募集カードと空き枠（日時と場所）を出す
4. 学ぶ側はカードを選び、空き枠をワンクリックで予約する（チケット1枚を仮押さえ）
5. 当日、決めた場所で会う
6. 学ぶ側が「完了」を押すと、チケットが話した人に移る（お礼コメントも送れる）
7. **双方が安全レビューに回答する**（相手には見えない）

## 3. 機能一覧

| 分類 | 機能 |
|---|---|
| 認証 | 大学メール（許可したドメインのみ）＋6桁のワンタイムコードでのログイン |
| さがす | 分野・学部・キーワード・形式・時間での検索、異分野のカードを優先表示 |
| 募集 | 募集カードの作成、空き枠（オフィスアワー）の登録 |
| 予約 | 即時予約、キャンセル（チケット返却）、完了、お礼コメント |
| チケット | 残高・履歴、毎月の配布 |
| マイページ | 教えた実績・お礼コメントの一覧 |
| 安全 | 下の「4. 安全・防犯システム」のとおり |
| 運営 | 通報・安全レビューの確認、一時停止・永久凍結、大学への通報の記録 |

## 4. 安全・防犯システム

### 4.0 基本方針

学内限定だからといって安全とは限りません。宗教・ビジネスの勧誘、出会い目的の利用、ハラスメントは学内でも起こりえます。
Campus-Cross は次の3段階、6つの仕組みで、**悪用を「させない・続けさせない・逃がさない」**ことを目指します。

| 段階 | ねらい | 仕組み |
|---|---|---|
| **1. 事前の予防** | 個人の特定と、不安なマッチングを防ぐ | ① 本名非公開（ニックネーム＋学部・学年のみ）<br>② 同性限定リクエスト |
| **2. 対話中の安全** | 密室にしない・長引かせない | ③ 学内パブリックスペース（＋Zoom）限定・最長30分 |
| **3. 事後の厳罰** | 大学メール認証を使って強く牽制する | ④ 相互の安全レビュー<br>⑤ 1回の不適切行為で即・永久凍結<br>⑥ 大学関係部署への通報 |

すべての仕組みは**画面での制限だけでなく、データベース側でも強制**しています。そのため、画面を経由せずに操作されても規則を破れません。

### 4.1 事前の予防

#### ① 本名非公開（ニックネーム＋学部・学年のみ）

SNS で個人を特定されたり、会う前に接触されたり、つきまとわれたりするのを防ぎます。

| 情報 | 他の利用者に見えるか |
|---|---|
| ニックネーム（表示名） | 見える |
| 学部・学年・分野 | 見える |
| 自己紹介・募集カード | 見える（連絡先は書けない） |
| アバター | 見える（写真ではなく、自動で作るイラスト） |
| 本名 | **そもそも登録しない** |
| 学科・専攻 | **登録しない**（人数が少なく特定につながるため） |
| 大学メールアドレス・通知用メールアドレス | 見えない（本人と運営のみ） |
| 性別 | 見えない（本人と運営のみ。同性限定の判定にだけ使う） |

**システム上の制限**
- 自己紹介・カード・予約時のひとこと・お礼コメント・待ち合わせの目印に、**メールアドレス・電話番号・URL・SNSのID（@〜）・「LINE交換」「インスタ」などの語を書くと保存できない**（データベースで拒否）
- ニックネームに学籍番号のような数字の並び（5桁以上）は使えない
- カードもプロフィールも、ログインしていない人や学外の人には表示しない

#### ② 同性限定リクエスト

「異性と2人で話すのは不安」という人のための設定です。

- プロフィールの「安心設定」で「同性からの申し込みのみ受け付ける」をオンにできる
- オンにした人のカードは、**異性の人、性別を回答していない人には一覧に表示されず、申し込むこともできない**
- オンにした人自身も、同性の人にだけ申し込める
- この設定を使うには、性別（女性／男性）の申告が必要。性別は他の利用者には表示されない
- 判定はデータベースで行い、画面に返すのは「申し込めるかどうか」だけ（相手の性別は返さない）

> **制約**：性別は自己申告で、大学の記録とは照合していません。また「回答しない」を選んだ人や、女性／男性以外の性自認の人は、この設定を使えません（今後の課題）。

### 4.2 対話中の安全

#### ③ 学内パブリックスペース限定（密室化・長時間化の排除）

- 実施場所は **「学食」「図書館フリースペース」「キャンパス内カフェ」「Zoom」の4つからしか選べない**（自由入力の場所欄はない）
- 待ち合わせの目印（例：「入口すぐのテーブル」）だけは書けるが、「研究室」「個室」「自宅」「部屋」「寮」「ホテル」「カラオケ」「車」などの語を含むと保存できない
- 1回は**最長30分**（データベースで30分を超える枠は作れない）
- Zoom の URL は、話す人と予約した人にだけ表示する（一覧や他の人には出さない）
- 予約画面に「当日の約束」を表示する（場所から移動しない、時間を守る、連絡先の交換は求めない・断ってよい）

### 4.3 事後の厳罰

#### ④ 相互の安全レビュー

セッションの開始時刻を過ぎると、**話した側・聞いた側の両方**に安全レビューへの回答をお願いします（ホームにも案内を表示）。

| 項目 | 内容 |
|---|---|
| 全体の印象 | 安心して話せた／少し気になった／問題があった |
| 気になったこと（複数選択） | 出会い目的・デートや飲みの誘い／連絡先やSNSのしつこい要求／勧誘（宗教・ビジネス・団体）／ハラスメント・身体への接触／決めた場所以外への誘導／テーマと関係ない話ばかり／時間を大きく超えた引き止め／相手が来なかった |
| 自由記述 | 運営に伝えたいこと |

- 回答は**相手には一切見えない**（運営だけが確認する）。そのため、仕返しを恐れずに書ける
- 「問題があった」、または深刻な項目（上の表の前半5つ）にチェックがあると、**自動で運営の確認待ちの通報として登録**される
- 1つの予約につき1人1回まで回答できる
- 星の数による公開評価はしない（評価のプレッシャーで、教える人が減るのを避けるため）

#### ⑤ 1回の不適切行為で即・永久凍結

ハラスメント・勧誘・出会い目的の行為が**運営の確認で1度でも認められたら、猶予なしで永久凍結**します。

**永久凍結の効果**（運営が操作すると同時にすべて実行）
1. その人のカードをすべて非公開にする
2. 入っている予約をすべて取り消し、相手のチケットを返す。まだ始まっていない枠も取り消す
3. **ログインできなくする**（認証サーバー側で利用停止にし、今のログイン状態も無効にする）
4. **同じ大学メールアドレスでは登録し直せない**（凍結したアドレスは、暗号学的ハッシュ値の形で保存する）
5. 対応の記録（誰が・いつ・どの通報に基づいて・確認した事実）を残す

**自動の一時停止（確認までの安全策）**
- **別々の2人以上**から深刻な内容の通報・安全レビューが届いたら、運営の確認を待たずに自動で一時停止する
- 一時停止中は、予約・カードの公開・枠の登録ができず、その人のカードは一覧から消える
- 運営が確認し、事実なら永久凍結、事実でなければ解除する

> **なぜ「通報1件で即凍結」にしないか**：嘘の通報で気に入らない相手を凍結させる、という悪用を防ぐためです。凍結の判断は運営が通報・安全レビュー・予約の記録などから事実を確認して行い、確認できた時点で猶予なく実行します。運営が誤りに気づいた場合に限り、記録を残したうえで解除できます。

#### ⑥ 大学関係部署への通報

利用者は全員、大学が発行したメールアドレスで本人確認をしています。そのため、運営は問題を起こした利用者を大学の窓口に伝えることができます。この「学内での信用を失い、処分を受けるかもしれない」というリスクが、悪用への強い牽制になります。

| 項目 | 内容 |
|---|---|
| 対象 | 悪質なケース（例：ハラスメント・執拗な勧誘・出会い目的の誘いが確認されたもの） |
| 通報先 | 大学の関係部署（学生支援の窓口、ハラスメント相談窓口など。**大学と調整中**） |
| 提供する情報 | 大学メールアドレス・表示名・学部・学年・通報と安全レビューの内容・日時（規約で定めた範囲に限る） |
| 根拠 | 登録時に、利用規約で「悪質な場合は大学に通報し、その際に上記の情報を提供する」ことへの同意を得る |
| 記録 | 運営画面で、通報先の部署・内容の要約・通報した日を記録する |

> **言葉の正確さについて**：確認しているのは「その大学メールアドレスを使える人であること」です。教職員や、卒業後もアドレスが残っている人、アカウントの貸し借りまでは区別できません。そのため「身元が100%特定できる」とは言わず、「大学が発行したアドレスで本人確認している」と説明します。

```

 通報する ───────────────┐
 安全レビューで             ├─→ 通報として登録 ─→ 別々の2人以上？ ─Yes→ 自動で一時停止
 深刻なサインを選ぶ ───────┘                         │                     │
                                                    No                     ▼

                                                                      必要なら当事者に確認）
                                                                           │
                                         ┌─────────────────────────────────┼──────────────────────┐
```

### 4.5 そのほかの安全の仕組み

- **学内メール認証**：許可した大学ドメインのメールだけ登録できる。登録後、学外のアドレスへの変更もできない
- **通報・ブロック**：予約の画面からいつでも通報できる。ブロックした相手・された相手とは予約が成立しない
- **学外非公開**：カード・プロフィールはログインした学内の利用者にしか見えない
- **利用規約への同意**：登録時に必須。規約を変えたら、次のログインで再同意を求める
- **緊急時の案内**：ガイドラインに「身の危険を感じたら、その場を離れて警察（110番）や大学の窓口・警備に連絡」と明記している

### 4.6 想定される質問と回答

**Q. 実際に事件が起きたらどうしますか？**
A. 身の危険がある場合は、まず警察と大学への連絡を案内します（ガイドラインに明記）。サービス側では、加害側のアカウントを永久凍結し、大学の窓口に通報します。記録（予約の日時・場所、通報と安全レビューの内容、対応の記録）は残っているので、大学や警察から求めがあれば提供できる体制を整えます（提供の手続きは大学と調整）。

**Q. 密室で会うことはありませんか？**
A. 場所は学食・図書館フリースペース・キャンパス内カフェ・Zoom からしか選べず、目印の欄に「研究室」「個室」「自宅」などを書くこともできません。当日に別の場所へ誘導されたら、安全レビューと通報の対象になります。

**Q. 出会い目的の利用はどう防ぎますか？**
A. 本名・写真・連絡先を出さない、連絡先を書き込ませない、同性限定を選べる、という仕組みで入口を狭めています。そのうえで、安全レビューで「出会い目的・デートや飲みの誘い」を検知し、確認できたら1回で永久凍結し、大学へ通報します。

**Q. 嘘の通報で他人を陥れることはできませんか？**
A. 通報が1件あっただけでは凍結しません。運営が記録をもとに事実を確認してから処分します。確認までの一時停止も、別々の2人以上から深刻な通報があったときに限ります。虚偽の通報は、規約で禁止事項にしています。

**Q. 個人情報はどう管理していますか？**
A. 下の「5. 個人情報の取り扱い」のとおりです。データベースでは、行ごとのアクセス制御（Row Level Security）によって、本人と運営以外は個人情報を読めないようにしています。

**Q. 運営は誰がしますか？**
A. Phase 1 は、開発者（学生）が運営を兼ねます。運営の権限は、データベースで個別に付けた人だけが持ちます。対応はすべて記録に残ります。

## 6. 技術構成とセキュリティ

| 項目 | 内容 |
|---|---|
| 画面 | Next.js（Vercel でホスティング） |
| 認証・データベース | Supabase（認証は大学メールのワンタイムコード、データベースは PostgreSQL） |
| アクセス制御 | 全テーブルに Row Level Security を設定し、本人・当事者・運営だけが必要なデータを読める |
| 重要な処理 | 予約・チケットの移動・安全レビュー・凍結は、すべてデータベース内の関数でまとめて実行し、画面から直接書き換えられない |
| 検証 | データベースの規則と画面の操作を、自動テストで確認している（同性限定・場所の制限・連絡先の拒否・自動停止・凍結・大学への通報記録を含む） |

## 7. 大学と相談・確認したいこと

1. **通報の受け皿**：悪質なケースをどの部署（学生支援・ハラスメント相談など）に、どの方法で伝えればよいか
2. **情報提供の可否と手続き**：提供してよい情報の範囲、同意の取り方（規約の文面）が適切か
3. **利用規約・プライバシーポリシーの確認**：法務的な確認を受けられるか
4. **大学メールの扱い**：教職員・卒業生のアドレスを区別する方法があるか（学生用のドメインや学籍番号の形式など）
5. **場所の指定**：「学食」「図書館フリースペース」「キャンパス内カフェ」として、具体的にどの施設を案内してよいか（施設側の了承）
6. **緊急時の連絡体制**：事件・事故が起きたときの大学側の窓口
7. **広報への協力**：学内での告知や、初期の協力者（教える側の学生）の募集

## 8. 現状の制約と今後の課題

- 性別は自己申告で、照合していない。女性／男性以外の性自認の人は同性限定を使えない
- 連絡先の検出は文字のパターンによるもので、言い換え（例：「ら い ん」）まではすべて防げない。安全レビューと通報で補う
- 実際に決めた場所で会ったかどうかは、システムでは確認できない（安全レビューで確認する）
- 運営の体制が小さいため、通報への対応時間の目標（例：48時間以内に初回確認）は、運営の人数に合わせて決める
- 高校生の受け入れ（無料）と高校向けの有料サービス（9章）は、未成年との接触にあたるため、9.2 の安全の前提を整えてから始める

## 9. 今後の展開（構想）

学生どうしの交換は無料のまま、高校生向けは「個人の高校生には無料」「高校（学校）には有料」の2つに分けて展開する予定です。どちらも構想段階で、現在のサービスにはまだ入っていません。

| 区分 | 対象 | 料金 | 内容 |

### 9.1 高校向け有料サービスの考え方

- 学生どうしのチケットの仕組みとは切り離す。チケットは今後も換金・購入できない
- 申し込みと契約は学校単位で行い、高校生と大学生が個人どうしでお金をやり取りすることはない
- 提供の形は未定。候補は、オンラインの座談会、学校への出張授業、学部ごとの紹介コンテンツなど
- 大学生への還元は未定（謝礼を払うか、実績として記録するか）。謝礼を払う場合は、「お金を介さない」という基本方針との整理と、報酬の扱い（雇用か業務委託か、税金）の確認が必要

### 9.2 未成年を受け入れるための安全の前提（検討中）

高校生の受け入れは、無料・有料のどちらも未成年との接触にあたるため、今の安全の仕組みに加えて次を前提にします。

- 1対1にしない（大学生2人以上、または教員・保護者が同席する）
- 学校経由での参加を基本とし、個人で参加する高校生には保護者の同意を必須にする
- 高校生と大学生の間で連絡先を交換できないようにする（今の連絡先の書き込み禁止を続ける）
- 高校生から受け取る個人情報は最小限（学校名・学年程度）にする
- 担当する大学生は、研修を受けて誓約に同意した人に限る

### 9.3 大学・相談窓口に確認したいこと

- [ ] 有料サービスで大学名（広島大学）を出してよいか。許可が必要か
- [ ] 学生が報酬を受け取る場合の扱い（大学の規程、雇用か業務委託か）
- [ ] 事業の主体（個人事業か法人化か）と、学校と契約するための体制
- [ ] 未成年を扱うときに必要な保険、規約、保護者同意の形
